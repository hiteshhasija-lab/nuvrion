# Reproducible application image build

`deploy/Dockerfile` builds the Nuvrion API with production-only lockfile dependencies and copies only runtime application, module, provider, contract, and migration content. It has no default base image: release engineering must pass an approved Node 24 image by immutable digest as `NODE_IMAGE`. The runtime uses the unprivileged `node` account and includes a readiness health check. The production Compose profile adds a read-only filesystem, dropped capabilities, resource limits, and private data-service networking.

Before building, use a clean immutable source commit and set `NUVRION_BUILD_VERSION`, `NUVRION_SOURCE_REVISION`, and `NUVRION_NODE_BASE_IMAGE`. Generate the input record with `node tools/create-build-provenance.js create <manifest.json>`, then verify it immediately before the build. Build with BuildKit using `docker build --build-arg NODE_IMAGE="$NUVRION_NODE_BASE_IMAGE" --file deploy/Dockerfile --tag <temporary-tag> .`. Do not use `latest`, a mutable base tag, or a dirty source tree.

In the approved registry pipeline, scan operating-system and JavaScript dependencies, generate an SPDX or CycloneDX SBOM, sign the resulting image digest with the organizational signing service, attach the provenance and SBOM as attestations, and enforce verification at deployment. Record the final application digest in the staging environment and rerun staging preflight. Registry publication, vulnerability acceptance, and signing require authorized release infrastructure and are not performed by repository tooling.

Repository tooling can generate the deterministic application dependency SBOM before the external build: run `node tools/generate-sbom.js create <sbom.cdx.json>`, with `NUVRION_SOURCE_REVISION` set to the immutable commit, and then run the same command with `verify`. The CycloneDX 1.6 document includes every locked production package, package URLs, available lockfile integrity hashes, and a dependency fingerprint. The release pipeline must supplement it with the base-image operating-system SBOM and vulnerability results, then attach both to the final image digest.

The local workstation used for this preparation does not provide a Docker client, so the image must be built and tested in the approved CI or release environment. Required runtime checks are container startup as non-root, readiness transition, read-only filesystem operation, graceful termination, and absence of development files or secrets in image layers.
